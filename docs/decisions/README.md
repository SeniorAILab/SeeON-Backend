# Architecture Decision Records

Architecture Decision Records (ADRs) capture significant technical choices in this project: the context that forced the decision, the option selected, the alternatives weighed, and the trade-offs accepted. ADRs are the authoritative record of _why_ the architecture looks the way it does.

## Lifecycle

```
Proposed → Accepted → Deprecated
```

Each ADR is the single current, self-complete decision for its **topic**. When a decision changes, edit the ADR in place and add a `## Changelog` line; git holds the history. Relationships between distinct atomic ADRs use `References`/`Refines` links. No supersede chains, coverage matrices, or retired-source tracking.

**Topic granularity — domain-scoped ADRs are allowed.** A topic is a cohesive area, not a single sentence. One ADR may record **several small, tightly-related decisions that belong to the same domain** when splitting them produces a cluster of stubs that are only meaningful together and are always read as one (e.g. ADR-008 holds the whole version-control domain: worktree lifecycle + PR size gate + type auto-label). The MECE test is applied **between** ADRs (no two ADRs relitigate the same choice), not as a one-decision-per-file rule. A choice that genuinely stands alone and would be referenced independently still gets its own ADR; do not bundle unrelated domains to save numbers.

**Folding.** When same-domain decisions that were split across ADRs are consolidated into one, move their content into the owning ADR, delete the absorbed files, repoint inbound references, and record the fold in the owning ADR's `## Changelog`. This is the one sanctioned reason an ADR file is removed.

Numbering: ADR numbers are stable topic anchors, assigned sequentially and **never reused** — including absorbed numbers. A folded ADR's number is retired (not reassigned); its anchor is forwarded by the absorbing ADR's `## Changelog` entry.

## Category ontology

Active/current-effective ADRs live in exactly one of four top-level categories:

Every ADR ends with a `## Changelog` section (one line per change). Optional `References`/`Refines` links express relationships to other ADRs.

| Category                   | Meaning                                                                                                                                                                                                 |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [`ml/`](./ml/)             | ML project decisions: data, models, training, demo, serving, ML experimentation, and ML-local deployment constraints.                                                                                   |
| [`backend/`](./backend/)   | NestJS/backend decisions: API, persistence, alerting, webhook, backend policy, and database integration.                                                                                                |
| [`frontend/`](./frontend/) | Product frontend/dashboard decisions for repository path `front/`.                                                                                                                                      |
| [`common/`](./common/)     | Strict common decisions that still constrain at least two of `ml`, `backend`, and `frontend` after attempted split, or repo-wide process/tooling decisions. Not a dumping ground for unclear ownership. |

## Provider review stance

Claude Code, Codex, and Gemini may be used as advisory review lanes for ADR placement, omission checks, link validation, and common-gate challenges. No provider is merge authority. Final authority is the current ADR corpus, validated links/diff, and human review.
